# Портфельный трекер — спецификация и план разработки

Версия: 1.0 · Статус: утверждена к реализации · Основной документ проекта.

Этот файл — единственный источник правды по требованиям. Любое отклонение фиксируется в `docs/DECISIONS.md`, прогресс — в `docs/PROGRESS.md`.

---

## 1. Продукт в одном абзаце

Веб-приложение для учёта личного инвестиционного портфеля. Пользователь ведёт активы двух типов: централизованные (котируются, цены тянутся из нашей базы) и кастомные (депозиты, наличные, недвижимость — параметры задаёт сам). Все показатели считаются от списка операций, поэтому историю можно править задним числом. Полный учёт движения денег необязателен: новичок просто добавляет позиции, продвинутый включает кошельки и ведёт всё до копейки.

Прототип смотри здесь - https://github.com/ulad220/klipatest2/blob/main/design/prototype.html

## 2. Зафиксированные решения

| № | Вопрос | Решение |
|---|---|---|
| D-01 | Многопользовательность | Полная изоляция. Один пользователь = один портфель. Шаринга и ролей внутри портфеля нет |
| D-02 | Себестоимость | FIFO (лоты) |
| D-03 | Доходность | TWR (истинный, по дневным снимкам) + XIRR |
| D-04 | Комиссия при покупке | Увеличивает себестоимость, валюта = валюта сделки. При продаже — уменьшает выручку |
| D-05 | Числа | `Decimal128` везде. `float` запрещён на всех слоях |
| D-06 | Глубина истории цен | Полная история инструмента в базе. Дата операции раньше начала истории — запрещена валидацией |
| D-07 | Тикер | Однозначен: один инструмент = одна биржа = одна валюта. Мультилистинг не поддерживается |
| D-08 | Сплиты | Детект через провайдера → модерация админом → применение ко всем портфелям операцией `SPLIT_ADJUST` |
| D-09 | Дивиденды (централизованные) | Тянутся автоматически, каждую операцию можно отредактировать или удалить вручную |
| D-10 | Процент по кастомным | Сложный только при `reinvest = true`, иначе простой |
| D-11 | Периодичность начислений | `{unit: week/month/year, count: N}` — «раз в 3 месяца», «раз в 7 месяцев» и т.п. |
| D-12 | Налог | Поле `taxRate` в настройках дохода, удержание отдельной операцией |
| D-13 | Погашение | Если «учитывать в наличных» — тело в кошелёк. Иначе операция создаётся со статусом `needs_decision` и висит в ленте до решения пользователя |
| D-14 | Прошлые начисления | При создании актива с датой первого начисления в прошлом генерируются все пропущенные начисления до сегодня |
| D-15 | Правка условий дохода | Автоматически ничего не перегенерируется. Есть явное действие «Пересчитать проценты по новой ставке» с выбором даты, с которой пересчитывать |
| D-16 | Регистрация | Открытая, с подтверждением email и сбросом пароля. Первый админ — через `scripts/create-admin.sh` |
| D-17 | Провайдеры | Настраиваемый приоритет и цепочка фолбэка. Данные API приоритетнее данных из CSV |
| D-18 | Yahoo Finance | Неофициальный API — приемлемый риск для пет-проекта. Обязателен фолбэк на другого провайдера |
| D-19 | CSV при наложении дат | Диалог выбора для всей загрузки целиком: «перезаписать всё» или «пропустить пересечения» |
| D-20 | Валюта портфеля | Меняется в настройках, вызывает полный пересчёт снимков |
| D-21 | Кошелёк | Привязан к портфелю и валюте, не к месту хранения. Может уходить в минус |
| D-22 | Экспорт и удаление аккаунта | Обязательны |
| D-23 | Оценка кастомных активов | Ручная операция «переоценка» |
| D-24 | Валюты MVP | USD, EUR, RUB, BYN, PLN |
| D-25 | Состав базы инструментов | Белый список, ведёт админ: загрузка списка тикеров файлом + ручная форма |
| D-26 | Backend | NestJS + Mongoose + TypeScript |
| D-27 | Вёрстка | Адаптивная, приоритет — десктоп |
| D-28 | Email в MVP | Только регистрация и сброс. Напоминания и сводка — код есть, включаются тумблерами в админке |
| D-29 | Внешние потоки для TWR | Покупка/продажа **без** галочки «из наличных» + пополнение/снятие кошелька. Сделка **с** галочкой — внутреннее движение, потоком не считается |
| D-30 | Снимки портфеля | Дневные снимки кэшируются в базе, инвалидируются от даты правки. Первоисточник — по-прежнему список операций |
| D-31 | Обмен валют | Отдельный тип операции `FX_EXCHANGE` между кошельками по курсу пользователя |
| D-32 | Заявки на тикер | Пользователь может запросить добавление инструмента, заявка падает в админку |
| D-33 | Крипта | Приоритетный источник — CoinGecko, фолбэк — Yahoo |
| D-34 | OpenFIGI | Исключён. ISIN и прочие идентификаторы вводятся вручную вместе с тикером |
| D-35 | Акции и ETF | Основной источник Yahoo, фолбэк Stooq, затем Börse Frankfurt |
| D-36 | `endOfMonth` | Применяется только к периодам в месяцах и годах, для недель поле скрыто. Даты считаются от якоря, а не от предыдущего начисления (см. 6.1) |
| D-37 | Порядок разработки | Сначала полностью работающие кастомные активы, затем CSV, затем провайдеры, затем почта |

Открытые вопросы — см. раздел 16.

## 3. Стек и топология

```
                    nginx-proxy-manager (внешний, чужая сеть)
                              │
        ┌─────────────────────┴─────────────────────┐
        │                                           │
  frontend (nginx:alpine)                    backend (node:22-alpine)
  Vue 3 + Vite + TS                          NestJS + Mongoose
  Pinia, vue-i18n, vue-router                BullMQ (воркеры)
  Chart.js                                          │
                                             ┌──────┴──────┐
                                          mongo:7        redis:7
                                       (реплика-сет rs0)  (очереди)
```

В dev-компоуз добавляется `mailhog` — все письма перехватываются локально, реальный SMTP не нужен до этапа 11.

- **Docker Compose**, отдельные контейнеры: `frontend`, `backend`, `worker`, `mongo`, `redis`.
- `worker` — тот же образ, что и `backend`, другая точка входа. Крон и тяжёлые пересчёты живут там, чтобы не блокировать API.
- Наружу порты не публикуются. Контейнеры подключены к внешней docker-сети `npm_network`, `nginx-proxy-manager` проксирует на них по имени сервиса.
- Mongo поднимается **одноузловым реплика-сетом** — без этого нет транзакций, а они нужны для атомарной записи связанных операций.
- Redis нужен для BullMQ (бэкфилл, пересчёты, рассылка). Если принципиально хочется обойтись без него — очередь можно сделать на коллекции Mongo, но это будет хуже; решение зафиксировано в пользу Redis.

**Версии:** Node 22 LTS, MongoDB 7, Vue 3.5, NestJS 11.

## 4. Модель данных (MongoDB)

Общие правила:

- Все денежные и количественные величины — `Decimal128`. В коде — обёртка `Money`/`Qty` поверх `decimal.js`, сериализация в строку в JSON. **Никаких `Number` для денег.**
- Даты операций — **дата без времени** (`Date` в UTC-полночь). Это снимает все вопросы с часовыми поясами при начислениях.
- Порядок операций внутри одного дня определяется полем `seq` (инкремент в рамках дня), иначе FIFO недетерминирован.
- Удаление — мягкое (`deletedAt`), кроме удаления аккаунта.

### 4.1 users

```js
{
  _id, 
  emailHash,        // HMAC-SHA256(email, PEPPER) — уникальный индекс, по нему логин и поиск
  emailEnc,         // AES-256-GCM(email) — для отправки писем и показа в админке
  emailMasked,      // "iv***@gmail.com" — для списков в админке без расшифровки
  passwordHash,     // argon2id
  role,             // 'user' | 'admin'
  status,           // 'pending' | 'active' | 'blocked'
  locale,           // 'ru' | 'en'
  emailVerifiedAt, lastLoginAt, createdAt, updatedAt,
  deletionRequestedAt
}
```

**Важно:** пароль хешируется, а не шифруется (в исходном ТЗ была формулировка «зашифрованы» — это ошибка). Email шифруется обратимо, но искать по нему можно только через `emailHash`, иначе логин перестанет работать.

### 4.2 portfolios

```js
{
  _id, userId,             // 1:1, уникальный индекс
  name, baseCurrency,      // 'USD' | 'EUR' | 'RUB' | 'BYN' | 'PLN'
  settings: {
    walletsEnabled,        // включается автоматически при первой операции с наличными
    defaultUseCash,        // предзаполнение галочки в форме сделки
    costBasis: 'FIFO'
  },
  recalcFrom,              // дата, с которой снимки грязные; null = всё актуально
  recalcStatus,            // 'clean' | 'queued' | 'running' | 'failed'
  createdAt, updatedAt
}
```

### 4.3 instruments — централизованные активы (глобальный справочник)

```js
{
  _id, ticker, exchange, currency,
  type,                    // 'stock' | 'etf' | 'bond' | 'metal' | 'crypto'
  name: { en, ru },
  isin,
  providerRefs: { yahoo: 'AAPL', moex: null, frankfurt: null, metals: null },
  priceProviderChain: ['yahoo', 'frankfurt'],   // null = взять глобальный приоритет по типу
  status,                  // 'draft' | 'backfilling' | 'active' | 'stale' | 'disabled'
  historyFrom, historyTo,  // фактические границы истории в prices
  lastSyncAt, lastError,
  createdBy, createdAt
}
```

Пользователю в поиске отдаются только `active`. Инструмент со `status = backfilling` невидим — иначе появится позиция без цен.

### 4.4 prices

```js
{ _id, instrumentId, date, close, source, isManual, importJobId, createdAt }
```

Уникальный индекс `{instrumentId: 1, date: 1}`. Хранится **сырая цена закрытия**, без корректировок на сплиты — иначе прошлая доходность пользователей будет меняться задним числом при каждом сплите.

Политика пропусков: если на дату цены нет (выходной, праздник, остановка торгов) — берётся последняя известная более ранняя. Если разрыв больше 7 календарных дней, позиция помечается флагом «цена устарела» в интерфейсе и инструмент переходит в `stale`.

### 4.5 fx_rates

```js
{ _id, base, quote, date, rate, source }   // уникальный { base, quote, date }
```

Храним попарно для всех сочетаний из D-24 — пять валют, 20 упорядоченных пар — либо кросс-курсом через USD — реализация на выбор, но интерфейс `getRate(from, to, date)` обязан отдавать прямой курс и уметь инвертировать. Пропуски заполняются последним известным курсом.

### 4.6 corporate_actions

```js
{
  _id, instrumentId, type,      // 'split' | 'reverse_split' | 'dividend'
  exDate, payDate,
  ratio: { num, den },          // для сплита 4:1 → num 4, den 1
  amountPerShare, currency,     // для дивиденда
  status,                       // 'pending' | 'approved' | 'rejected' | 'applied'
  detectedBy, sourcePayload,
  reviewedBy, reviewedAt, appliedAt,
  affectedPortfolios            // счётчик для админки
}
```

### 4.7 assets — позиции в портфеле

```js
{
  _id, portfolioId, kind,        // 'central' | 'custom'
  instrumentId,                  // только для central
  type,                          // для custom: 'deposit' | 'bond' | 'cash' | 'realty' | 'other'
  name, currency,
  custody: { country, holder },  // holder — свободный текст с автокомплитом
  income: {                      // только custom, при «приносит постоянный доход»
    enabled, autoPost,
    incomeType,                  // 'interest' | 'coupon' | 'dividend' | 'rent'
    rateType,                    // 'percent_annual' | 'fixed_amount'
    rate,
    period: { unit, count },     // 'week' | 'month' | 'year' + N
    anchorDay,                   // день месяца из firstAccrualDate, хранится явно
    endOfMonth,                  // применяется только к month/year, см. 6.1
    firstAccrualDate, maturityDate,
    reinvest, taxRate, toCash,
    dayCount                     // 'ACT/365' по умолчанию
  },
  status,                        // 'open' | 'closed' | 'matured'
  notes, createdAt, updatedAt, deletedAt
}
```

### 4.8 operations — единственный первоисточник

```js
{
  _id, portfolioId, assetId, date, seq, type,
  quantity, price, amount,        // amount = quantity × price для сделок
  currency,
  fee, feeCurrency,
  useCash,                        // сделка проведена через кошелёк
  walletCurrency,                 // для операций с наличными
  tax, taxCurrency,
  status,                         // 'normal' | 'needs_decision'
  source,                         // 'manual' | 'auto' | 'import' | 'corporate_action'
  idempotencyKey,                 // для авто-начислений, уникальный разреженный индекс
  generatedFrom,                  // ссылка на правило/корпоративное действие
  notes, createdAt, updatedAt, deletedAt
}
```

**Типы операций:**

| Тип | Что делает | Влияет на кошелёк |
|---|---|---|
| `BUY` | Добавляет лот | Только если `useCash` |
| `SELL` | Закрывает лоты по FIFO, фиксирует прибыль | Только если `useCash` |
| `INCOME` | Проценты / купон / дивиденд / аренда | Если `toCash` или `useCash` |
| `FEE` | Комиссия вне сделки | Да |
| `TAX` | Удержанный налог | Следует за `INCOME` |
| `REVALUATION` | Новая оценка кастомного актива | Нет |
| `PRINCIPAL_IN` | Пополнение депозита | Если `useCash` |
| `MATURITY` | Погашение, закрытие позиции | По D-13 |
| `WALLET_IN` / `WALLET_OUT` | Ввод и вывод денег | Да |
| `FX_EXCHANGE` | Обмен между кошельками | Да, обе валюты |
| `SPLIT_ADJUST` | Коррекция количества после сплита | Нет |

### 4.9 lots — производные, кэш FIFO

```js
{ _id, portfolioId, assetId, openOpId, openDate, quantity, remainingQty,
  costPerUnit, feeAllocated, closedByOps: [], closedAt }
```

Полностью пересобираются движком пересчёта. Руками никогда не редактируются.

### 4.10 snapshots — дневные срезы

```js
{
  _id, portfolioId, date,
  totalValue,                     // в валюте портфеля
  byAsset: [{ assetId, quantity, price, valueNative, valueBase }],
  byCurrency: [{ currency, value }],
  wallets: [{ currency, balance }],
  externalFlow,                   // сумма внешних потоков за день, в валюте портфеля
  dailyReturn, twrIndex,          // накопительный индекс TWR
  investedCost, realizedPnl, unrealizedPnl,
  computedAt
}
```

Уникальный индекс `{portfolioId: 1, date: 1}`.

### 4.11 Служебные коллекции

- `custody_places` — `{userId, country, holder, usageCount}` для автокомплита.
- `sync_runs` — журнал прогонов провайдеров: провайдер, тип задачи, статус, счётчики, ошибки, длительность.
- `import_jobs` — загрузки CSV: файл, режим наложения, отчёт валидации, результат.
- `ticker_requests` — заявки пользователей на добавление инструмента.
- `app_settings` — единый документ: приоритеты провайдеров, расписания кронов, тумблеры писем, лимиты.
- `email_tokens` — `{userIdHash, tokenHash, purpose, expiresAt, usedAt}`, одноразовые.
- `refresh_tokens` — ротация, привязка к устройству, отзыв.
- `audit_log` — действия админа: кто, что, до/после.
- `notifications` — внутренние уведомления пользователю (в т.ч. «требует решения»).

## 5. Расчётное ядро

Самая ответственная часть системы. Выносится в отдельный модуль `backend/src/engine`, покрывается юнит-тестами в первую очередь, не зависит от HTTP-слоя.

### 5.1 Конвейер пересчёта

```
operations (сортировка по date, seq)
      ↓ применение по порядку
   lots (FIFO)  +  wallets  +  realized P&L
      ↓ для каждого дня от startDate до сегодня
   позиции на дату × цена на дату × курс на дату
      ↓
   snapshots (стоимость, потоки, дневная доходность, индекс TWR)
      ↓
   агрегаты (TWR за период, XIRR, разбивки)
```

### 5.2 Инвалидация

При любом создании, правке или удалении операции:

```
portfolio.recalcFrom = min(portfolio.recalcFrom, operation.date, previousDateIfMoved)
→ задача в очередь
```

Воркер удаляет снимки от `recalcFrom` и пересобирает их вперёд. Лоты пересобираются целиком (их немного, оптимизация преждевременна). Смена валюты портфеля или применение сплита ставит `recalcFrom` в дату первой операции.

Пока пересчёт идёт, интерфейс показывает бейдж «обновляем расчёты» и последние актуальные цифры, а не пустоту.

### 5.3 FIFO

- `BUY`: создаётся лот, `costPerUnit = (quantity × price + fee) / quantity`.
- `SELL`: списываются самые ранние лоты. `realizedPnl = proceeds − fee − Σ(consumedQty × costPerUnit)`.
- Продажа большего количества, чем есть на дату, — ошибка валидации с указанием доступного остатка.
- `SPLIT_ADJUST` умножает `quantity` и `remainingQty` открытых лотов на `num/den` и делит `costPerUnit` на тот же коэффициент. Итоговая себестоимость лота не меняется.

### 5.4 TWR

Для каждого дня, где `V[d−1] > 0`:

```
r[d] = (V[d] − CF[d]) / V[d−1] − 1
```

`CF[d]` — сумма внешних потоков дня (D-29), приведённая к валюте портфеля по курсу этого дня. Потоки считаются пришедшими в начале дня.

```
TWR(период) = Π(1 + r[d]) − 1
```

Дни, где `V[d−1] = 0` (портфель ещё пуст или полностью распродан), из произведения исключаются, разрыв фиксируется в снимке флагом.

### 5.5 XIRR

Ньютон-Рафсон с фолбэком на бисекцию в диапазоне ставок от −0.99 до 10. Потоки: внешние потоки со знаком минус для вводов, плюс для выводов, плюс терминальная стоимость портфеля на конец периода. Если знак потоков не меняется — возвращается `null`, интерфейс показывает «недостаточно данных», а не ноль.

### 5.6 Оценка активов на дату

| Тип | Как оценивается |
|---|---|
| Централизованный | `prices[instrumentId, date]`, с переносом последней известной цены вперёд |
| Кастомный с переоценкой | последняя `REVALUATION` с датой ≤ date |
| Кастомный без переоценки | цена покупки (для депозита — тело + капитализированные проценты) |
| Наличные в кошельке | номинал |

Пересчёт в валюту портфеля — по `fx_rates` на ту же дату.

### 5.7 Точность

Хранение — `Decimal128`. Внутренние вычисления — `decimal.js` с 20 значащими цифрами. Округление только на выводе: количество до 8 знаков (крипта), деньги до 2 (кроме крипто-валют кошелька), проценты до 2. Округление half-up.

## 6. Начисления и планировщик

### 6.1 Расписание

Из `income` собирается детерминированный ряд дат: старт — `firstAccrualDate`, шаг — `period.count × period.unit`, конец — `maturityDate`.

Флаг `endOfMonth` осмыслен не для всех периодов, поэтому правила заданы явно:

| Единица | `endOfMonth` | Правило |
|---|---|---|
| `week` | не применяется, поле скрыто в форме | Тот же день недели, шаг `count × 7` дней |
| `month` | `false` | Тот же день месяца, что и `anchorDay`. Если в целевом месяце такого дня нет — последний день этого месяца, **но якорь не сдвигается**: 31 янв → 28 фев → 31 мар |
| `month` | `true` | Всегда последний календарный день целевого месяца |
| `year` | `false` | Та же дата. 29 фев в невисокосный год → 28 фев, якорь остаётся 29 фев |
| `year` | `true` | Последний день месяца-годовщины: 15 мар 2024 → 31 мар 2025 → 31 мар 2026 |

Ключевой момент — **якорь**. Наивная реализация «прибавить месяц к предыдущей дате» после февраля навсегда съезжает на 28-е число. Поэтому дата каждого начисления считается от `firstAccrualDate` и порядкового номера периода, а не от предыдущей даты.

В интерфейсе поле подписывается по контексту: для месяцев — «начислять в последний день месяца», для года — «начислять в конце месяца годовщины», для недель не показывается вовсе.

### 6.2 Идемпотентность

`idempotencyKey = "${assetId}:accrual:${scheduledDate}"` с уникальным индексом. Перезапуск воркера, двойной крон, ручной ретрай — дубля не создадут никогда.

### 6.3 Сумма начисления

```
base       = reinvest ? (тело + капитализированные проценты) : тело
grossAmount = rateType === 'percent_annual'
              ? base × rate × дней_в_периоде / dayCountBase
              : fixedAmount
tax         = grossAmount × taxRate
net         = grossAmount − tax
```

Тело берётся на дату начисления с учётом всех `PRINCIPAL_IN` до неё. При `reinvest = true` начисление увеличивает тело, при `false` — не увеличивает, а `net` уходит в кошелёк (если `toCash`) или просто фиксируется как доход.

### 6.4 Догенерация прошлого

При создании актива с `firstAccrualDate` в прошлом воркер сразу генерирует всю цепочку до сегодняшнего дня (D-14). Для депозита десятилетней давности это сотни операций — генерация идёт пачкой в одной транзакции, интерфейс показывает прогресс.

### 6.5 Правка условий

Изменение `income` **не трогает** созданные операции (D-15). В карточке актива появляется действие «Пересчитать проценты по новой ставке» с выбором даты: авто-начисления от этой даты удаляются и генерируются заново. Ручные начисления не трогаются никогда — их пользователь вносил сам.

### 6.6 Погашение

В `maturityDate` создаётся `MATURITY`, актив переходит в `matured`. При `toCash = true` тело падает в кошелёк. Иначе операция получает `status = 'needs_decision'`, попадает в ленту с плашкой «укажите, куда пошли деньги» и в блок «Требует внимания» на дашборде. Варианты решения: в кошелёк / вывел из портфеля / реинвестировал в другой актив (выбор актива).

### 7.2 Приоритеты и фолбэк

В `app_settings` хранится цепочка по типу актива и по валютным парам, например:

```
stock/etf → [yahoo, stooq, frankfurt]
crypto    → [coingecko, yahoo]
metal     → [metals, yahoo]
RUB-пары  → [moex, nbrb]
BYN-пары  → [nbrb]
PLN-пары  → [nbp, yahoo]
```

Бумаги Варшавской биржи (GPW) тянутся через `yahoo` с суффиксом `.WA` — отдельный адаптер под GPW не нужен.

Провайдер считается упавшим при HTTP-ошибке, таймауте или пустом ответе на непустой запрос. Тогда берётся следующий, инцидент пишется в `sync_runs`. Если упала вся цепочка — уведомление админу и алерт в панели.

### 7.3 Кроны

| Задача | Расписание | Что делает |
|---|---|---|
| `fx-daily` | 06:00 UTC | Курсы за вчера по всем парам |
| `prices-daily` | 22:00 UTC | Закрытия по всем `active` инструментам |
| `crypto-intraday` | каждые 4 ч | Крипта торгуется круглосуточно |
| `corporate-actions-scan` | 03:00 UTC | Ищет сплиты и дивиденды, кладёт в `pending` |
| `accruals` | 01:00 UTC | Начисления на сегодня по всем портфелям |
| `snapshots-refresh` | 02:00 UTC | Досчитывает вчерашний день всем портфелям |
| `backfill` | по требованию | История нового инструмента |

Все расписания редактируются в админке без передеплоя.

### 7.4 Приоритет источников

API перезаписывает значения, пришедшие из CSV (D-17). Поле `isManual` при этом сбрасывается, факт перезаписи попадает в `sync_runs`. Логика: CSV — способ закрыть дыру, пока провайдер молчит, а не источник истины.

### 7.5 Скорректированные цены и смешение источников

Провайдеры отдают разные ряды: Yahoo умеет и сырое закрытие, и скорректированное, Stooq — только скорректированное. Смешивать их в одном ряду нельзя: получится скачок на дату сплита или дивиденда, который движок примет за реальное движение цены.

Правила:

- В `prices` добавляется поле `priceKind: 'raw' | 'adjusted'` и `source`.
- У инструмента хранится `priceKind`, зафиксированный при первом успешном бэкфилле. Провайдер из цепочки, который не умеет отдать такой же вид цены, для этого инструмента не используется — фолбэк пропускается, а не подставляет чужой ряд.
- Смена вида цены по инструменту возможна только полным перезаливом истории с пересчётом всех затронутых портфелей. Это ручное действие админа с подтверждением.
- Целевой вид — `raw` (D-08). `adjusted` допускается там, где сырых цен взять негде, но тогда сплиты по этому инструменту не применяются вручную: коэффициент уже зашит в ряд, применение `SPLIT_ADJUST` даст двойную коррекцию. Инструмент помечается флагом `autoAdjusted`, модерация сплитов для него отключена.

### 7.6 Импорт CSV

Формат: `date,ticker,close[,currency]`. Разделитель — запятая или точка с запятой (автоопределение), даты — ISO, десятичный разделитель — точка.

Пайплайн: загрузка → парсинг → валидация (существует ли тикер, корректны ли даты и числа) → **отчёт до записи**: сколько строк валидно, сколько с ошибками, сколько пересекается с существующими данными → выбор пользователя «перезаписать всё» или «пропустить пересечения» (D-19) → запись пачками → итоговый отчёт с выгрузкой отбракованных строк.

Затронутые инструменты помечают все портфели с этими активами как требующие пересчёта.

## 9. Фронтенд

**Стек:** Vue 3 (Composition API) + TypeScript + Vite, Pinia, vue-router, vue-i18n, Chart.js, VeeValidate + Zod.

**Экраны:**

1. **Дашборд** — общая стоимость, изменение за день/период, TWR и XIRR, график стоимости, аллокация, последние операции, блок «Требует внимания».
2. **Активы** — таблица с группировкой по типу/валюте/месту хранения, разворачивающиеся строки с лотами.
3. **Карточка актива** — параметры, график, все операции, действия.
4. **Операции** — общая лента с фильтрами и поиском, отметки авто-операций.
5. **Кошельки** — появляются только после первой операции с наличными (иначе скрыты полностью).
6. **Настройки** — валюта портфеля, язык, экспорт, удаление аккаунта.
7. **Админка** — отдельный раздел: пользователи, инструменты, цены, курсы, корпоративные действия, импорты, журналы, настройки.

**Формы добавления активов** — точно по ТЗ: тип → поля. Поле «где хранится» двухступенчатое (страна → посредник), посредник с автокомплитом по ранее введённым.

**i18n:** ru и en с первого дня, ключи в `locales/*.json`, никаких строк в шаблонах. Форматирование чисел, дат и валют через `Intl` с учётом локали. Язык переключается в шапке и хранится в профиле.

**Дизайн:** источник — `design/prototype.html` из репозитория. На этапе 0 из него вытаскиваются токены (цвета, типографика, отступы, радиусы, тени) в `src/styles/tokens.css`, дальше компоненты собираются только на токенах.

## 10. Безопасность

- Пароли — argon2id (`memoryCost` 64 МБ, `timeCost` 3).
- Email — AES-256-GCM, ключ и pepper в `.env`, в репозитории только `.env.example`.
- Access-токен 15 минут, refresh 30 дней с ротацией и отзывом всей цепочки при повторном использовании старого токена.
- Rate limit: логин 5/мин на IP и на аккаунт, сброс пароля 3/час, регистрация 5/час на IP.
- Токены подтверждения и сброса — одноразовые, живут 24 ч и 1 ч соответственно, хранятся хешами.
- Валидация всего входящего через DTO + `class-validator`; `mongo-sanitize` против инъекций в запросы.
- helmet, строгий CORS по списку доменов, CSP без `unsafe-inline`.
- Каждый запрос к данным портфеля проверяет `portfolio.userId === req.user.id` на уровне сервиса, а не только гварда.
- Админские действия пишутся в `audit_log`.
- Удаление аккаунта: мягкая метка + физическое удаление через 30 дней, экспорт данных доступен до этого момента.

## 12. Этапы разработки

Порядок подчинён одной цели: **работающий продукт на кастомных активах как можно раньше**, без зависимости от внешних API и почты. Депозиты, наличные, недвижимость, начисления и доходность — всё это считается на своих данных, поэтому полезное приложение появляется уже на этапе 6. Централизованные активы, провайдеры и рассылки навешиваются сверху на готовое ядро.

Каждый этап — отдельная ветка `stage/NN-slug`, самодостаточен, заканчивается работающим приложением. Агент, начинающий работу, читает `SPEC.md` + `docs/PROGRESS.md` и берёт первый незакрытый этап.

**Опорные точки:**

- Этап 6 — трекер кастомных активов, которым уже можно пользоваться каждый день.
- Этап 8 — работают централизованные активы, цены заливаются файлом.
- Этап 9 — цены обновляются сами.
- Этап 11 — почта, приложение готово к посторонним пользователям.

### Этап 3 — Расчётное ядро

**Цель:** цифры, которым можно верить.

- Инвалидация от `recalcFrom`, очередь пересчёта, индикатор «обновляем расчёты» в интерфейсе.
- Стоимость портфеля, вложено, реализованная и нереализованная прибыль, разбивки по типу, валюте, стране, месту хранения.
- Интерфейс оценки написан двумя реализациями: `CustomAssetValuation` (готова) и `MarketAssetValuation` (заглушка, включается на этапе 7).
- Золотые наборы: частичные продажи, покупка задним числом, мультивалютность, дыра в оценке.

**DoD:** список активов показывает стоимость и P&L. Правка операции пятилетней давности перестраивает историю. Тесты ядра зелёные.

---

### Этап 4 — Кошельки и деньги

- Кошельки по валютам, `WALLET_IN` / `WALLET_OUT`, `FX_EXCHANGE` (D-31), отрицательные балансы.
- Галочка «взять из наличных / вернуть в наличные» в формах сделок.
- Раздел кошельков скрыт полностью до первой денежной операции.
- Смена валюты портфеля в настройках с полным пересчётом (D-20).

**DoD:** новичок кошельков не видит; после включения баланс сходится с лентой копейка в копейку; смена валюты портфеля не ломает историю.

---

### Этап 5 — Начисления

- Генератор расписания по правилам 6.1 (якорь, `endOfMonth` для месяцев и лет, недели), идемпотентные ключи, крон начислений.
- Простой и сложный процент, налог, догенерация прошлого (D-14).
- Погашение, статус `needs_decision`, блок «Требует внимания», разрешение операции.
- Действие «Пересчитать проценты по новой ставке» (D-15).
- Ручное добавление процентов, купонов, дивидендов.

**DoD:** депозит с датой начала два года назад мгновенно получает всю цепочку начислений; двойной запуск крона дублей не создаёт; погашение без галочки «в наличные» повисает в блоке решений; ряд «раз в 3 месяца с 31 января» идёт 31.01 → 30.04 → 31.07, а не съезжает на 28-е.

---

### Этап 6 — Доходность и дашборд · **первый цельный продукт**

- TWR по снимкам, XIRR, доходность за период и по каждому активу.
- Графики: стоимость во времени, доходность, аллокация, переключатели периодов.
- Дашборд целиком по прототипу, карточка актива, полировка мобильной вёрстки.

**DoD:** TWR и XIRR сходятся с эталонным расчётом на трёх кейсах, включая портфель с полной распродажей в середине периода. Приложением можно пользоваться для реального учёта депозитов, наличных и недвижимости — этап закрывается только после недели личного использования.

### Этап 7 — Централизованные активы (ручной режим)

- `instruments`, `prices`, статусы инструментов, `priceKind` (7.5).
- Админка: CRUD инструментов, загрузка списка тикеров файлом (D-25), ручной ввод цен и курсов.
- Таблица цен с пагинацией и поиском по дате — требование ТЗ.
- Включение `MarketAssetValuation` в движке, форма добавления централизованного актива, поиск инструментов, валидация даты по границам истории (D-06).
- Заявки на добавление тикера (D-32).

**DoD:** админ заводит инструмент и вбивает десяток цен руками, пользователь добавляет по нему позицию, она попадает в общую стоимость и доходность наравне с кастомными активами.

### Этап 8 — Импорт CSV

- Загрузка, парсинг, валидация, отчёт до записи, выбор режима при наложении (D-19), запись пачками, отчёт после.
- Выгрузка отбракованных строк, история импортов, пометка затронутых портфелей на пересчёт.

**DoD:** файл с намеренными ошибками и пересечениями обрабатывается в обоих режимах без потерь и дублей. С этого момента централизованные активы полноценно работают вообще без внешних API.

### Этап 9 — Провайдеры данных

- Замена ручных курсов автоматическими.

**DoD:** добавленный тикер сам подтягивает историю и становится `active`; отключение основного провайдера переводит выгрузку на фолбэк, инцидент виден в журнале; курсы валют обновляются без участия человека.

### Этап 10 — Корпоративные действия

**DoD:** сплит 4:1 применяется одним действием админа, количество бумаг меняется у всех, историческая стоимость до даты сплита остаётся прежней.

## 13. Протокол передачи между сессиями

Токенов одной сессии не хватит на весь проект, поэтому состояние держится в репозитории.

**`docs/PROGRESS.md`** — обновляется в конце каждой сессии:

```markdown
## Текущий этап: 3 — Расчётное ядро
Ветка: stage/03-engine

### Сделано
- [x] FIFO-лоты + тесты
- [x] Позиции на дату

### В работе
- [ ] Дневные снимки — написан билдер, нет инвалидации
      Файлы: backend/src/engine/snapshot.builder.ts:120

### Следующий шаг
Инвалидация от recalcFrom + подписка на события операций

### Заметки и грабли
- Decimal128 не складывается напрямую, только через decimal.js
- Курс BYN у НБРБ отдаётся за 100 единиц для RUB — делить
```

**`docs/DECISIONS.md`** — короткие ADR на каждое отклонение от спецификации: контекст, решение, последствия.

**Правила для агента:**

1. Прочитать `SPEC.md` и `docs/PROGRESS.md` целиком до первой строки кода.
2. Работать только внутри текущего этапа. Задел на будущие этапы не делать.
3. Не менять сигнатуры модуля `engine` без записи в `DECISIONS.md`.
4. Каждый этап заканчивается зелёными тестами и обновлённым `PROGRESS.md`.
5. Формат данных из спецификации менять нельзя — если он не подходит, сначала правка `SPEC.md`, потом код.

## 16. Открытые вопросы

1. **Валюты сверх пяти.** PLN добавлен (D-24), польские бумаги и счета поддерживаются. Но GBP, CHF, JPY, CNY, KZT по-прежнему нет — ETF в фунтах или франках добавиться не сможет. На данный момент и не нужно.
2. **Налоговая отчётность.** Не нужно
3. **Импорт операций пользователем.** Не нужно
4. **Хранение исторических остатков наличных.** Сейчас кошелёк оценивается по номиналу, инфляция и проценты на остаток не учитываются. И хорошо.
5. **История крипты глубже года.** Бесплатный тариф CoinGecko отдаёт только последние 365 дней. Для позиции, купленной в 2017, история берётся разово из Yahoo или заливается CSV, дальше ряд поддерживает CoinGecko.
6. **Часовой пояс пользователя.** Даты операций хранятся без времени, но «сегодня» для крона и интерфейса определяется по UTC. Для пользователей в UTC+3 и западнее это иногда даёт расхождение на день. Расхождение принимается
